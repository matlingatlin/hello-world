# Code review — 2026-08-21

A full read of the repo against what Scio says it is: *input → a professional app you own*,
built cheaply and provably (`docs/STRATEGY.md`, `docs/PRODUCT-OVERVIEW.md`). Written after the
first end-to-end real build driven from outside the sandbox.

**Shape:** engine 17.3k lines / 32 test files, api 3.4k / 11, app 4.9k / 6, shared 785.
Suites green: engine 587 + 6 skipped, api 97, app 74, ruff and typecheck clean.

**The short version.** The engine is the strongest part of this codebase and the guardrails are
real — the gates, the instrumentation verifier, the honest status, `unjudged`, the 404-not-403
tenancy rule. What is missing clusters in two places, and both are load-bearing for the pitch:
**cost is measured but never enforced or fully counted**, and **the product ends at the reveal** —
every button there leads to a placeholder.

---

## Correctness — the four that matter

### 1. A build has no spend ceiling — `budget_usd` is plumbed and never set
**Severity: high.** The relay enforces a budget (`execution/relay.py:214`) and `BuildOptions`
carries the field (`builder/loop.py:254`) — but the only construction on the real path,
`builder/pipeline.py:234`, leaves it `None`. Nothing in `apps/api` sets one either.

So the estimate is shown, the user approves, and no code compares spend against it while the build
runs. The evidence is already in the CHANGELOG: a build estimated $1.05–$2.51 spent **$2.69** and
nothing intervened. Chunked codegen (B076) and the new split (2026-08-21) both *increase* the
number of calls a stuck package can make.

**Fix:** pass a budget derived from the approved estimate's high end plus a margin, and surface
exceeding it as a first-class outcome — "stopped at your ceiling, here is what was built" — not an
exception. This is the difference between an estimate and a promise, and STRATEGY sells the promise
("know the cost up front").

### 2. Every dollar spent in the design window is invisible
**Severity: high.** `usageEvent.create` exists in exactly one place — `build.service.ts:249`, the
delivery build. A preview build and every directed change are real model calls costing real money,
and `design.service.ts` records neither. The data is *right there* and dropped:
`DesignChangeResult.total_cost_usd` (`design/change.py:77`) is returned by the engine and never
read by the api; the preview build's `finished` event carries `total_cost_usd` and only
`app_url`, `manifest`, `whole` and `git_sha` are kept.

The design window is where STRATEGY expects most interaction to happen ("directed changes in
seconds"). Billing built on this ledger would undercount the majority of spend, and B073's "a
build's actual cost is recorded" is true only of delivery builds.

**Fix:** meter the preview build and each applied change the same way `persist()` does, and show a
running total in the design window. Cheap — the numbers already arrive.

### 3. Two builds can run on one project, and they share a directory
**Severity: high.** `build.service.run` (`build.service.ts:138`) checks for a current spec and
computes `number` from a read, then starts. Nothing refuses a second concurrent build:
- the version number is a read-then-write race — two builds compute the same `number`;
- worse, the engine keys the workspace by project id and `prepare_workspace(project_id, fresh=True)`
  (`builder/workspace.py:349`) **wipes it**, so a second build deletes the first one's files
  mid-flight;
- and both spend money.

The trigger is not exotic. It is exactly what this session did: the stream looked dead ("network
error") while the build ran on, and the natural reaction is to press Build again.
`project.status` is already set to `"building"` — it is simply never read.

**Fix:** refuse to start when the project is already building (409 with "a build is already
running, open it"), and make the build-version number a database-side sequence rather than
`max + 1` in application code.

### 4. `applyWorkspaceScope` fails open for operations it does not understand
**Severity: medium (latent — no current caller).** `auth/workspace-scope.ts:36`: `upsert` is listed
under CREATE_OPERATIONS but an upsert has no top-level `data` (it has `create`/`update`), so
nothing is stamped and nothing is filtered; `createMany` is explicitly skipped
(`!Array.isArray(next.data)`). Both would write unscoped rows on a workspace-scoped model.

Nothing calls either today — verified — so this is a trap, not a hole. But it is a trap in the one
file that exists to make tenancy impossible to get wrong.

**Fix:** invert the default. Enumerate the operations that *are* scopeable and **throw** on anything
else touching a `WORKSPACE_SCOPED_MODELS` entry. A loud failure in development beats a silent
cross-tenant write in production.

## Honesty and UX — where the product stops

### 5. The reveal's three buttons all lead to a placeholder
**Severity: high (product, not code).** `RevealPage.tsx:179-185` sends the user to `/live` and
`/ship`; `App.tsx:14` lists both — plus `/settings`, `/versions`, `/notifications` — as
`PlaceholderPage`: *"This screen is being ported from the prototype next."*

So after a build that cost real money, **every** next step is a dead end. The MVP claim is "an app
you own", and ownership is precisely the screen that does not exist. This is now the single
largest gap between what the product does and what it says.

Related: `/settings` being a placeholder means model and pass-count are not user-controllable
(B049) — the cost lever STRATEGY calls a Settings control is editable only by hand in
`apps/engine/.env`. This session hit that: without the three extra lines the default profile is
*matrix ranking, 4 passes*, several times dearer, and a user has no way to see or change it.

### 6. A dropped connection still reads as a failed build
**Severity: medium.** Fixed at the cause today (the api's SSE now has a keep-alive), but the
message remains wrong for the case that survives it. `DesignPage.tsx:152` and the build screen
report a network failure as *"The build stopped"* / *"The preview could not be built."* — about a
build the server is still running. The build screen one line above promises "You can leave this
page — the build keeps running", and then contradicts itself.

**Fix:** distinguish "we lost the connection" from "the build failed", and reconnect rather than
declare. The state is already re-readable — `getDesign` and `build/latest` both return it.

## Cost and quality — the moat, unstarted

### 7. Prompt caching is not implemented, and chunking made it worth more
`grep` finds no `cache_control` anywhere in the engine. STRATEGY calls it *"our single biggest cost
lever"* and files it under "Adopt now (clear wins, low risk)": cache reads at ~0.1× input.

Every build-package prompt carries a large static prefix — playbook, house rules, architecture
slice, canonical vocabulary — and B076's chunking, plus today's split, multiply how many times that
prefix is sent. A package emitted in three chunks pays for the same prefix three times. The lever
grew while it went unpulled. (B055.)

### 8. There is still no measurable quality gate at the reveal
B048. STRATEGY's C5 — Lighthouse, accessibility, security scan, shown as scores — is described as
something no competitor does, and the reveal currently shows "4 of 5 parts work" with no external
measure at all. The infrastructure exists: a preview is already running and Playwright is now a
declared extra, so a Lighthouse run has somewhere to point.

## The craft — how well is this written?

Measured, not felt. Engine 668 functions; app 8 pages; api 11 services.

### What holds up

**Type safety is unusually strict for a codebase this young.** Across all TypeScript source:
**one** `any` (in `workspace-scope.ts`, the one place that must be generic over Prisma's arg
shapes), **one** real `as never`, and **zero** `@ts-ignore`. Most projects this age are riddled
with escape hatches. This one is not.

**The tests describe the product, not the methods.** *"names a marking it cannot address instead of
dropping it"*, *"sends every pending marking plus the prompt as ONE change"*, *"does not offer a way
back to one that was never committed"*. A failure names a broken promise, not a broken function.
1,268 engine assertions, 334 api, 159 app.

**Function length is disciplined** — 19 of 668 engine functions exceed 60 lines — and the module
split is coherent: `builder` 3.5k, `library` 2.9k, `core` 2.3k, `layerc` 1.8k, `intake` 1.8k,
`layerb` 1.3k, `execution` 0.9k, `design` 0.8k. Each is a thing you can name.

### Four places the craft slips

**1. The four biggest functions are the four most important ones.**
`build_package` (**226 lines**, `builder/loop.py:527`), `verify_instrumentation` (167),
`stream_full_build` (163), `stream_build_plan` (143). `build_package` alone holds the attempt loop,
the snapshot/rollback, five gates, the critique call, remainder collection and persistence — six
responsibilities in one scope. That is where the last three bugs lived: the chunk retry that never
shrank, the Playwright import that never asked, the observation that could not say it never
happened. Not a coincidence. The gates are already separate functions; the attempt body wants to be
one too, so the loop reads as *try → judge → decide*.

**2. "Make this the current version" is written four times and none of them is transactional.**
`spec.service` (twice), `design.service.record:114`, `build.service.persist:206`. Each one reads
every row, un-flags the current one, then creates a new one with `number = max + 1`. A crash between
the un-flag and the create leaves a project with **no** current version; two callers at once leave
two, or duplicate numbers. `provisioning.service.ts:26` already uses `$transaction`, so the pattern
is known here — it just is not applied to the invariant that matters most. One helper inside a
transaction, or a partial unique index (`unique (project_id) where is_current`) so the database
refuses the second row.

**3. The stream is the most important data path and the only one that opts out of the shared types.**
`packages/shared` exists to type the contract between three services — and every SSE payload travels
as `Record<string, unknown>` (65 occurrences) and is re-parsed at the far end with
`String(data.app_url ?? "")` (`DesignPage.tsx:139`). The build stream carries the packages, the
cost, the manifest and the preview URL, and none of it is typed end to end. This is not theoretical:
part of why the app could not tell a dropped connection from a failed build is that everything
arriving is an untyped bag. Give the events a discriminated union in `shared` and the app stops
guessing.

**4. `DesignPage.tsx` is 691 lines with 19 `useState`, 6 `useEffect`, 6 `useRef`.** Nineteen
independent pieces of state is a state machine written as loose variables; the legal combinations
are not expressed anywhere, so nothing stops *preparing + error + previewUrl* from being true at
once — which is roughly what the confusing screen in this session was. A reducer with named states
(`idle | building | ready | disconnected | failed`) would make the impossible combinations
unrepresentable, and would make §6 above almost fall out for free.

### A trade-off worth naming: 30% of the engine is prose

9,466 lines of code, 3,714 docstring lines, 418 inline comments. I would defend most of it — this
codebase explains *why*, which is the rare and valuable kind, and twice this week a comment
predicted a bug before it was found.

But some of it is **narrative history** sitting where a rule should be: `CHUNK_TOKEN_BUDGET`'s
docstring is eleven lines, of which four are the story of `pkg_feature_workout`. The story belongs
in the CHANGELOG (it is already there); the constant wants the rule. When the two are mixed, the
rule is harder to find and the comment ages badly — an incident from four months ago reads as
current. Suggested split: the rule and the invariant stay in the code, the incident moves to the
changelog, and the code cites it (`see CHANGELOG 2026-08-20, B076`). Worth a deliberate decision
either way rather than drift.

## What is genuinely good, and should not be traded away

- **The gates are real and they refuse.** Instrumentation loss fails the build and rolls back; the
  strict resolver keeps resolution server-side; the console classifier separates the app's noise
  from a third party's. These are the parts that make "professional" more than a word.
- **`unjudged` as a first-class concept.** A criterion nobody could check rides along instead of
  being dropped, so "works" means "works, and here is what nobody checked". Today's Playwright fix
  reuses the same idea. This is the codebase's best instinct and it should spread further — the
  spend ceiling in §1 should report the same way.
- **Tenancy is done correctly and consistently.** Every implemented service resolves the project
  through the scoped client first, and 404-not-403 is the right choice, reasoned in a comment.
- **The comments earn their place.** They record *why*, and repeatedly they record a real incident.
  Two bugs this week were found by reading a comment that predicted them.

## Recommended order

1. **§3 the concurrent-build guard** — cheap, prevents corruption and double spend.
2. **§2 meter the design window** — the numbers already arrive; this is plumbing.
3. **§1 the spend ceiling** — needs a decision on what to do at the limit (stop and keep, or stop
   and roll back), so it is worth an ADR.
4. **§5 the ship screen** — export/ownership is the MVP promise, and the biggest gap.
5. **§7 prompt caching** — the cost lever, now compounding with chunking.
6. **§4, §6** — the fail-closed scope helper and the connection-vs-failure wording.

§8 (quality scores) and fleet learning (B047) are the moat layers; they belong after the core loop
ends somewhere other than a placeholder.
